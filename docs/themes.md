# Visual themes

Ploff uses one shared DOM and one generated runtime stylesheet. Themes may change
colors, surfaces, typography, spacing, geometry, layout, and visibility, but theme
code must remain isolated so a change for one theme cannot leak into another.

## Sources of truth

- `app/theme-registry.js` defines every available theme, its body class, locale key,
  source stylesheet, and UI capabilities such as whether the user accent color applies.
- `app/styles/core.css` contains behavior and presentation genuinely shared by all
  themes. It may consume semantic theme tokens, but it must not contain a visual or
  layout exception for a specific theme.
- `app/styles/themes/<theme>.css` contains all theme-specific values and overrides.
- Current shipped themes are `classic`, `immersive`, `premiere`, `nova`, and `atelier`.
  `premiere` is premium-cinematic, `nova` is futuristic-tech, and `atelier` is
  minimal-luxury; all three newer directions use isolated layouts and legacy-safe
  motion rather than sharing a visual template.
- `app/styles.css` is generated by `npm run build:styles`. Never edit it directly.
- `app/index.html` loads one stylesheet only. Do not add runtime theme `<link>`
  switching or asynchronous CSS loading.

The browser must load `theme-registry.js`, then `settings-schema.js`, then
`settings.js`. `npm run check:styles` verifies that order because the persisted
Settings schema reads the theme registry during module initialization and Settings
reads the schema immediately afterwards.

## Theme isolation contract

Every selector in a theme file must start with that theme's body class. Example:

```css
body.visual-theme-immersive .home-preview { ... }
body.visual-theme-immersive.is-home-surface-active .content { ... }
```

Do not write this in a theme file:

```css
.home-preview { ... }
```

The contract checker rejects unscoped selectors, including selectors nested in
supported `@media`, `@supports`, or `@document` blocks.

Theme classes are mutually exclusive. Settings removes every registered theme class
before applying the selected one. The same code path is used at startup, after an
interactive theme change, and after loading saved settings.

The TV target remains Chrome 53. Theme-only effects should therefore be built from
well-supported primitives such as transforms, opacity, gradients, borders, box-shadow,
transitions, and ordinary `@keyframes`. Do not require CSS Grid, `backdrop-filter`,
container queries, modern color functions, or other newer CSS features to achieve a
theme look.

## Semantic tokens versus layout overrides

Use a semantic token when the same CSS property belongs to the same conceptual role
in every theme. The current required token set is:

```text
--theme-app-background
--theme-app-text
--theme-scroll-track
--theme-scroll-thumb
--theme-backdrop-shade
--theme-media-card-surface
--theme-card-caption-surface
--theme-corner-radius
```

Every registered theme must declare all required tokens in its scoped root rule.
`core.css` provides bootstrap fallbacks so the application remains readable before
JavaScript applies the body theme class, but theme files must not rely on those
fallbacks as their normal values.

Keep layout that is intentionally different inside the theme file. For example,
Immersive owns its Home preview geometry and content positioning directly in
`immersive.css`; those rules should not be converted into shared tokens merely to reduce
line count.

Home preview copy must not be artificially constrained to a narrow fraction of the TV.
When a theme renders the Home hero, its copy/title/summary should be allowed to use the
full horizontal space inside that theme's symmetric content gutters; title ellipsis is
a final overflow safeguard, not the primary layout mechanism. Theme-specific surfaces,
gradients, borders, and typography remain isolated in the theme stylesheet.

When introducing a new shared token:

1. give it a semantic name rather than a theme-specific name;
2. add a safe fallback to `:root` in `core.css`;
3. consume it only where the semantic role is genuinely shared;
4. add it to `REQUIRED_THEME_TOKENS` in `scripts/check-theme-contracts.js`;
5. define it explicitly in every existing theme before relying on it.

Do not use one broad token for components that only happen to share the same value
today. Independent components should stay independent unless their visual role is
actually coupled by design.

## Adding a theme

To add a theme called `neon`:

1. Register it once in `app/theme-registry.js`:

   ```js
   { id: 'neon', className: 'visual-theme-neon', labelKey: 'settings.themeNeon', styleFile: 'neon.css', supportsAccentColor: false }
   ```

2. Add `settings.themeNeon` to the English source locale and every other locale.
   Keep key and placeholder parity across all locales.
3. Create `app/styles/themes/neon.css` with a scoped root and all required tokens:

   ```css
   body.visual-theme-neon {
     --theme-app-background: #000;
     /* define every required theme token */
   }
   ```

4. Add any theme-specific component or layout overrides only under
   `body.visual-theme-neon ...` selectors.
   Set `supportsAccentColor: true` only when the theme is intentionally driven by the
   user's global accent; otherwise keep it `false` and own the palette in the theme.
5. Run:

   ```sh
   npm run build:styles
   npm run verify
   ```

No controller branch, settings `if/else`, extra stylesheet link, or dynamic loader is
required. If adding a theme requires one, stop and revisit the registry/theme
boundary instead of hardcoding the new ID.

## Modifying an existing theme

For a change that applies to one theme only, edit only that theme file. Do not alter
`core.css` to make a Immersive-only or Classic-only adjustment.

For a change intended for every theme, update `core.css`. If the shared rule needs a
value that varies by theme, introduce or reuse a semantic token and define the value
in every theme.

A DOM change affects all themes because the DOM is deliberately shared. After a DOM
change, inspect every registered theme and keep selectors resilient to the shared
structure.

## Runtime lifecycle

The visual theme is applied in three required flows:

- startup: Settings applies the saved theme before `ShellFeatureController.start()`;
- live change: the normal Settings save path applies the new class immediately;
- saved-settings load: loading settings runs the same save/apply path, for both
  same-device recovery and loading settings from another TV.

Regression coverage lives in `tests/test-application-composition.js` and
`tests/test-settings-controller.js`. `tests/test-theme-styles.js` covers registry,
CSS generation, required tokens, stylesheet isolation, the single-stylesheet runtime,
and script ordering.

## Generated files and verification

After editing theme source CSS, regenerate the stylesheet:

```sh
npm run build:styles
```

After editing coordinator JavaScript, regenerate the application bundle separately:

```sh
npm run build:app
```

`app/styles.css` and `app/app.js` are generated artifacts and must never be edited by
hand. Before handing work to another developer or Codex, run:

```sh
npm run verify
npm run test:memory
git diff --check
```

For visual changes, also perform a physical-TV smoke test of every registered theme,
with particular attention to focus, safe area, Home layout, Settings, Detail, Player,
and saved-settings loading.
